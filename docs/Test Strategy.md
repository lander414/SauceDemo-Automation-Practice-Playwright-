# Test Strategy

## 1. Automation Strategy
The automation strategy for SauceDemo is centered on validating critical end-to-end user journeys using Playwright and TypeScript. The framework uses a modular, maintainable approach with Page Object Model (POM) design to separate test logic from page interactions.

## 2. Test Levels
- Unit: Not the primary focus for this portfolio project
- Integration: Validates page interactions across components
- System / End-to-End: Covers core user flows such as login, product selection, cart, checkout, and logout

## 3. Test Types
- Functional testing
- Regression testing
- Smoke testing
- Negative testing
- UI validation

## 4. Browser Strategy
- Primary browser: Chromium
- Future expansion: Firefox and WebKit
- Test execution will be aligned with Playwright’s cross-browser capabilities

## 5. Data Management
- Use known demo credentials from SauceDemo
- Keep test data in a centralized and reusable structure
- Prefer deterministic test inputs to avoid flaky runs

## 6. Defect Management
- Defects will be logged with severity, priority, reproduction steps, and expected vs actual results
- Issues will be tracked in a structured bug report format for visibility and traceability

## 7. Reporting
- HTML reports will be generated by Playwright
- Screenshots and traces will be attached for failed scenarios
- Reports will support both execution review and portfolio presentation

## 8. CI/CD Readiness
The project is structured to be CI/CD ready through:
- Standardized test scripts
- HTML reporting
- Configurable environment variables
- Easy integration with GitHub Actions or similar pipelines

## 9. Coding Standards
- Use TypeScript for strong typing and readability
- Follow consistent naming conventions for files, test cases, and locators
- Keep tests concise, readable, and focused on business behavior

## 10. Naming Conventions
- Test files: descriptive names such as login.spec.ts or landing-page.spec.ts
- Test cases: clear business-oriented names
- Page objects: use PascalCase and domain-focused naming

## 11. Page Object Model Architecture
The framework follows a POM approach where:
- Page classes encapsulate UI interactions
- Test files contain scenarios and assertions
- Common helpers and config are separated from business logic
- This improves maintainability and reduces duplication
