# Test Strategy

## 1. Automation Strategy
The SauceDemo automation strategy validates critical user journeys with Playwright and TypeScript. The framework separates page interactions from scenario assertions through Page Object Model classes, shared fixtures, locators, and helpers.

## 2. Test Levels
- Unit: Not currently implemented in this repository
- Integration: Covered indirectly through page and fixture interactions
- System / End-to-End: Primary level; covers login, inventory, cart, checkout, sidebar, and logout

## 3. Test Types
- Functional testing
- Regression testing
- Smoke testing
- Negative testing
- UI validation

## 4. Browser Strategy
- Primary browser: Chromium
- Expansion path: Firefox and WebKit
- Current baseline: Chromium configured through Playwright

## 5. Data Management
- Use known SauceDemo demo credentials
- Keep reusable values in `utils/`, `config/`, and `test-data/`
- Prefer deterministic inputs and isolated test setup
- Do not commit real credentials or secrets

## 6. Defect Management
- Defects will be logged with severity, priority, reproduction steps, and expected vs actual results
- Issues will be tracked in a structured bug report format for visibility and traceability

## 7. Reporting
- HTML reports will be generated by Playwright
- Screenshots are captured only on failure; traces are captured on first retry
- Reports will support both execution review and portfolio presentation

## 8. CI/CD Readiness
The project is prepared for CI/CD through:
- Standardized test scripts
- HTML reporting
- Configurable environment variables such as `BASE_URL`
- Publishable `reports/` and `test-results/` artifacts
- Straightforward integration with GitHub Actions or similar pipelines

## 9. Coding Standards
- Use TypeScript for strong typing and readability
- Follow consistent naming conventions for files, test cases, and locators
- Keep tests concise, readable, and focused on business behavior

## 10. Naming Conventions
- Test files: descriptive names such as `login.spec.ts` or `LandingPage.spec.ts`
- Test cases: clear business-oriented names
- Page objects: use PascalCase and domain-focused naming

## 11. Page Object Model Architecture
The framework follows a POM approach where:
- Page classes encapsulate UI interactions
- Test files contain scenarios and assertions
- Common helpers and config are separated from business logic
- This improves maintainability and reduces duplication
